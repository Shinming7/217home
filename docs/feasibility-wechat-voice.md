# 微信小程序与游戏内语音可行性评估

- 日期：2026-10-28
- 范围：把 217之家做成微信小程序；在房间内加入语音频道/语音聊天
- 结论性质：工程与合规评估，不构成法律意见；平台规则会变化，提交前以微信后台要求为准

## 0. 结论

**微信小程序：技术可行，现阶段不建议直接做。**

原因不在代码量，而在三件事：需要第二个客户端、需要自有已备案域名、UGC/私信/语音类目对个人主体基本不开放。按当前规则，个人主体小程序不能提供社交、UGC、论坛、直播、音视频类服务；本项目包含照片墙、留言、私信和语音，正好全部落在受限范围。要以小程序形态上线，通常需要企业主体、ICP 备案、内容安全审核、举报与隐私机制，开发周期约 2–3 个月，审核还有驳回风险。

**游戏内语音：Web 端可行，朋友规模成本很低；小程序端不建议做。**

Web 端有两条路：自建 WebRTC（免费，但要处理信令、NAT 和 TURN）或接第三方 RTC（声网/腾讯 TRTC，接入快，每月有免费额度）。建议先做 6 人房间语音，登录后才能进，默认不录音。小程序语音需要非个人主体和实时音视频类目，个人主体基本走不通。

**推荐路线：**

1. 短期保留 Web，先做移动端 H5 体验与微信分享，不注册小程序。
2. 功能顺序建议 A 在线住户 + 站长移交 → B 站内消息/邀请 → C 鱼缸多人游戏 → D 语音房间。
3. 如果小程序是硬需求，先完成企业主体、域名备案和内容安全方案，再用 Taro 做 2 周技术验证，不要直接重写 Web。

**2026-10-28 已确认的决策：**

- 微信小程序：不做。
- 实时语音频道：不做；改用「按住说话、松手广播」的语音留言方案，评估见 §3.6。
- 鱼缸多人游戏：同时最多 8 人。
- 站长已由「积德」移交给「丢丢」，移交后建议丢丢立即轮换站长密匙。

## 1. 现状与约束

| 项目 | 现状 | 对小程序/语音的影响 |
| --- | --- | --- |
| 前端 | React 19 + Vite + Canvas 2D，自绘像素房间 | 小程序没有 DOM，Canvas API 与事件模型不同，房间渲染要重写 |
| 后端 | Qoder Sites Function（Deno）+ PostgreSQL + 私有 Storage | 可以继续提供 HTTPS API，但小程序请求域名必须配置且已备案 |
| 登录 | 昵称 + 个人密码 + 房间暗号，PBKDF2 哈希 | 小程序通常用 wx.login/openid，需要与现有身份绑定，不能直接替换 |
| 内容 | 照片、留言、即将增加的私信与邀请 | 属于 UGC，需要内容安全检测、举报、隐私协议 |
| 实时能力 | 目前用轮询同步在线状态与游戏房间 | 语音需要信令通道；轮询可用但体验不如 WebSocket/SSE |
| 域名 | 使用 `qoder.website` 平台域名 | 不适合作为小程序服务器域名，也不在你的备案主体下 |
| 数据要求 | 账号密码、照片、留言必须跨版本保留 | 任何新客户端都必须复用同一后端与成员 ID，不能另起账号体系 |

## 2. 微信小程序评估

### 2.1 必须重做的部分

| 模块 | 现状 | 小程序端工作量 |
| --- | --- | --- |
| 房间渲染 | Canvas 2D、16px 瓦片、像素精灵、光照与粒子 | 重写渲染循环与触摸输入；像素缩放、层级、性能都要重新调 |
| 界面 | React 组件 + CSS 弹窗 + 横屏布局 | 用 WXML/WXSS 或 Taro 组件重做；弹窗、滚动、安全区都要适配 |
| 登录 | 昵称 + 个人密码 + 暗号 | 增加 wx.login，处理 openid 与现有成员的绑定/迁移 |
| 照片 | 登录后签名 URL 查看原图 | 小程序 `<image>`/`downloadFile` 需要配置 download 合法域名，Storage 域名也必须可配置且已备案 |
| 留言/私信 | 文本 + 内容管理 | 接入内容安全检测，增加举报、拉黑、删除入口 |
| 小游戏 | Canvas 小游戏、轮询房间状态 | 输入与渲染适配；联机协议可复用，但网络层要改成 wx.request |
| 分享 | 浏览器链接 | 小程序分享卡片、群入口、场景参数；需要处理未登录用户进入 |

结论：即使逻辑层可以复用，房间渲染和小游戏输入仍然相当于第二个前端。用 Taro/uni-app 能复用 TypeScript 逻辑和 API 封装，但不能复用现有 DOM/CSS/Canvas 代码。

### 2.2 平台与合规门槛

| 门槛 | 要求 | 对本项目的影响 |
| --- | --- | --- |
| 小程序备案 | 境内小程序需备案；平台初审约 1–2 个工作日，管局审核约 1–20 个工作日 | 上线前至少预留 1–3 周 |
| 服务器域名 | 必须是 HTTPS，已 ICP 备案，并在小程序后台配置；不支持 IP 和端口 | 需要自有域名；`qoder.website` 平台域名不适合作为你的后端域名 |
| 业务域名（web-view） | 个人主体不支持配置业务域名，即个人小程序不能用 web-view 嵌网页 | 不能靠“套一层网页”绕过小程序重写 |
| 个人主体类目 | 个人主体不开放社交、UGC、论坛、直播、音视频等类目 | 照片墙、留言、私信、语音都在受限范围，审核大概率要求企业主体 |
| 内容安全 | UGC 需接入文本/图片/媒体内容安全检测，并有举报与处置机制 | 需要新增审核链路、举报入口、用户协议与隐私政策 |
| 登录与账号 | wx.login 换取 openid，服务端保存会话 | 需要把 openid 与现有 member 绑定，处理老用户首次进入 |
| 审核 | 社交/UGC/语音类审核更严，可能要求资质或补充说明 | 存在驳回与反复修改的时间成本 |

个人主体通常不能开通 `live-pusher`/`live-player` 等音视频组件；腾讯云的小程序 RTC 接入文档也明确要求先开通企业类小程序。也就是说，“小程序 + 语音”对个人开发者基本是双重门槛。

### 2.3 三种落地路径

| 路径 | 做法 | 优点 | 缺点 | 估算 |
| --- | --- | --- | --- | --- |
| A. 微信内 H5（推荐短期） | 保持现有 Web，优化移动端，用微信分享链接进入；必要时引导到系统浏览器 | 不审核、不备案新域名、代码复用高、当天可上线 | 不是小程序入口；微信内置浏览器的麦克风/WebRTC 支持要真机验证 | 1–2 人周 |
| B. Taro/uni-app 小程序（有企业主体再做） | 复用 TypeScript 逻辑与 API，重写房间渲染与界面；后端加 wx.login 绑定 | 有小程序入口、分享与消息能力；逻辑层复用 | 第二套前端；备案、类目、内容安全、审核；小程序语音仍受限 | 6–12 人周 + 1–3 周备案/审核 |
| C. 原生小程序重写（不推荐） | 全部用 WXML/WXSS/JS 重写 | 平台能力最完整 | 复用最低、维护两套代码、成本最高 | 10–16 人周 |

### 2.4 成本估算

以下按“朋友规模、非商业化”估算，仅供排期参考。

| 项目 | 估算 | 说明 |
| --- | --- | --- |
| 小程序前端适配 | 6–12 人周 | Taro 复用逻辑；房间渲染、小游戏、弹窗、触摸输入重写 |
| 后端改造 | 1–2 人周 | wx.login/openid 绑定、域名与图片下载配置、内容安全接口 |
| 小程序备案 | 1–3 周 | 平台初审 1–2 个工作日，管局 1–20 个工作日 |
| 认证费用 | 个人约 30 元/年，企业约 300 元/年 | 以微信后台当前政策为准 |
| 域名与证书 | 约 50–150 元/年 | 域名 + 免费 SSL 证书即可 |
| 内容安全 | 微信接口有免费额度与频率限制 | 第三方审核服务另计 |
| 审核 | 1–2 周，可能反复 | UGC/社交/语音类驳回风险高 |
| 总计 | 约 2–3 个月 | 不含语音商业化与长期内容运营 |

钱不是主要成本；主要成本是第二套客户端、备案合规和长期内容审核。

### 2.5 主要风险

1. **主体风险**：个人主体做社交/UGC/私信/语音，审核大概率不通过；企业主体也需要相应类目与资质。
2. **账号迁移风险**：openid 与现有 member 绑定出错，会造成重复账号或老用户回不到原身份。
3. **内容审核风险**：照片、留言、私信都可能出现违规内容；没有检测与举报机制会被下架。
4. **域名与 Storage 风险**：后端域名、图片下载域名都必须可配置且已备案；平台域名不一定能满足。
5. **双端维护风险**：Web 与小程序两套 UI、两套 Canvas，后续每个功能都要改两次。
6. **语音类目风险**：小程序语音需要非个人主体和实时音视频类目，个人主体基本不可行。
7. **平台依赖风险**：分享、登录、支付、内容安全都受微信规则变化影响。

### 2.6 Go / No-Go 条件

满足以下条件再启动小程序：

- 已确定企业主体，并能提供营业执照与类目所需资质。
- 已有自有域名并完成 ICP 备案，能绑定到后端与 Storage。
- 接受内容安全检测、举报/拉黑、隐私协议与用户协议的长期维护。
- 明确小程序是主要入口，而不是“顺便多一个入口”。
- 先用 Taro 做 2 周技术验证：登录绑定、进入房间、渲染 384×256 房间、打开一张照片，四项都跑通再继续。

不满足以上条件时，优先做微信内 H5 和分享卡片。

## 3. 游戏内语音评估

### 3.1 技术前置

- 全站 HTTPS；麦克风权限必须由用户手势触发（iOS Safari/微信内置浏览器尤其严格）。
- 需要一个信令通道交换 SDP/ICE；现有轮询可用，但建立连接会更慢，最好有 WebSocket/SSE。
- 需要 STUN 做 NAT 穿透；部分网络必须用 TURN 中继，否则连不上。
- 需要回声消除、静音/闭麦、说话高亮、设备切换、断线重连。
- 移动端切后台可能被系统挂起；微信内置浏览器对 WebRTC/麦克风的支持随版本变化，必须真机验证。
- 语音默认不录音、不落盘；如果要做录音/回放，隐私与合规成本会明显上升。

### 3.2 方案对比

| 方案 | 适用人数 | 费用 | 接入难度 | 优点 | 缺点 |
| --- | --- | --- | --- | --- | --- |
| WebRTC 网状 + 自建 TURN | ≤6 人 | STUN 免费；TURN 服务器约 30–100 元/月 + 流量 | 中 | 不依赖第三方、隐私可控、无按分钟费用 | 人数多时上行压力大；NAT/防火墙问题要运维 |
| 腾讯 TRTC | ≤6 人 | 每月 10,000 分钟免费（最长一年）；音频约 0.99 美元/千分钟 | 低 | SDK 成熟、回声消除与弱网好、接入快 | 依赖第三方；需要账号与合规配置 |
| 声网 Agora | ≤6 人 | 每月 10,000 分钟免费；音频约 7 元/千分钟 | 低 | 同上，文档与生态成熟 | 同上 |
| 小程序 live-pusher/live-player | 小范围 | 另计 | 高 | 微信原生组件 | 需要非个人主体与类目资质；个人主体不可用 |

价格会调整，接入前以服务商官网为准。

### 3.3 成本示例

6 位朋友，每人每天语音 60 分钟：

- 每月用量：6 × 60 × 30 = 10,800 分钟。
- 免费额度 10,000 分钟，超出 800 分钟。
- 按 7 元/千分钟计算，超出部分约 5.6 元/月。
- 如果每人每天 30 分钟：6 × 30 × 30 = 5,400 分钟，完全在免费额度内。

自建 TURN 的成本主要是服务器与流量：6 人网状连接约 30 路 32 kbps 音频，理论总带宽约 1 Mbps；一小时约 0.4 GB，朋友规模每月通常几十元以内。实际取决于有多少连接需要中继。

### 3.4 推荐方案

**先在 Web 端做「房间语音频道」，上限 6 人。**

- 进入频道需要已登录，沿用房间暗号与成员身份；频道内显示头像、名字、谁在说话。
- 默认闭麦，用户主动开麦；支持静音、退出、拉黑/举报。
- 默认不录音、不存储音频；隐私说明写清楚。
- 技术选型：
  - 想快：接腾讯 TRTC 或声网，1–2 人周可出可用版本。
  - 想省与可控：WebRTC + coturn，2–3 人周，需要一台小 VPS。
- 先做 2 台设备、跨网络的 spike，验证微信内置浏览器/Safari/Chrome 的麦克风与连通性，再决定是否全面做。

### 3.5 主要风险

1. 微信内置浏览器对麦克风和 WebRTC 的支持不稳定，可能只能引导到系统浏览器。
2. 部分网络必须走 TURN，否则语音连不上；需要监控 TURN 可用性。
3. 回声、底噪、设备切换会影响体验，需要成熟的音频处理。
4. 语音骚扰与隐私投诉；需要举报、拉黑、禁言与明确的不录音承诺。
5. 如果未来上小程序，语音要重新接一套 SDK/组件，Web 端成果不能直接复用。

### 3.6 替代方案：按住说话、松手广播（PTT 语音留言）

不做实时频道时，可以做成「语音留言」：按住按钮录音，松手后把音频上传，频道内其他人轮询到后点击播放。

| 项目 | 评估 |
| --- | --- |
| 实现方式 | 浏览器 `MediaRecorder` 录音 → 上传私有 Storage → 消息列表展示波形/时长 → 其他人播放 |
| 是否需要 WebRTC/TURN/信令 | 不需要；复用现有轮询与 Storage，基础设施零新增 |
| 延迟 | 松手后才上传，其他人最多等一个轮询周期（4 秒），不是实时对讲 |
| 成本 | 朋友规模接近零；一条 30 秒 Opus 语音约 60–90 KB，定期过期即可控制存储 |
| 兼容性 | Chrome/Edge/Firefox 可直接录 webm/opus；Safari 需 mp4 兜底；微信内置浏览器必须真机验证 |
| 播放限制 | 浏览器禁止自动播放他人音频，通常需要点击播放或做「播报队列」 |
| 内容管理 | 语音属于 UGC：站长删除、单条过期（如 7 天）、举报入口都要有 |
| 估算 | 后端存取 + 录音 UI + 播放列表 + 删除/过期，约 3–5 天 |

结论：PTT 语音留言适合插在消息中心里做一个附件类型，排在 M16 之后；如果要做「按住时对方立刻听到」的对讲，仍然回到实时语音的复杂度。

## 4. 与现有功能的衔接

- **消息中心**：私信与游戏邀请共用一张表；邀请携带游戏类型、房间 ID、过期时间；接受邀请直接进入对应房间。
- **语音频道**：复用登录会话与成员信息，不新建账号；频道状态只保存在内存/短期状态中，不写长期数据。
- **鱼缸游戏**：邀请走消息中心；房间状态复用 `game_state` 或新增短期房间表；不触碰成员、照片、留言数据。
- **小程序**：如果未来做，继续调用同一套 HTTPS API，成员 ID 与个人密码体系保持不变；任何数据库变更仍然只增不删。
- **数据保留**：新增表或可空列必须走新迁移（004 起），不得修改已应用的迁移，不得在发布流程中清空线上数据。

## 6. 决策与遗留问题

已确认：

1. 小程序不做；实时语音频道不做。
2. 鱼缸多人游戏上限 8 人。
3. 站长由「积德」移交给「丢丢」，移交后建议丢丢立即轮换站长密匙。

仍待确认：

1. PTT 语音留言是否要做、单条时长上限与保留天数（建议 60 秒、7 天）。
2. 消息中心的私信是否需要「站长不可读」的承诺与实现（建议需要）。
3. 鱼缸游戏的淘汰观战是否需要跨房间（建议只允许观战仍在场的玩家）。
